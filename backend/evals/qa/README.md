# Замер качества ответов chat_w_doc

Отвечает на вопрос «стало лучше или хуже» после правки промпта или узла. До этого
замера качество ответов не измерялось ничем: 59 тестов репозитория проверяют
механику стримов и ошибок, но не то, что навык отвечает.

Набор собран по замечаниям заказчика от 08.08.2026 (`ИФТ 08.08.26.docx`).

## Как устроен

Прогон идёт **боевым путём**: `DocumentService._prepare` → граф `document_process`
с настоящими промптами. Подменён только s3 — текст документов берётся из `docs/`
в том виде, в каком навык видит их в проде, то есть **обезличенным**.

Подменять `_prepare` нельзя: именно там решается, сколько документов доедет до
графа, и там же живёт обрезка «берём последний файл». Замер, обходящий подготовку,
показал бы зелёный отчёт на дефекте, из-за которого саммари делается по одному
документу из двух.

Проверки — детерминированные, без LLM-судьи: регулярки и подстроки. Такой замер
воспроизводим, стоит ноль и не спорит сам с собой между прогонами.

## Запуск

Запускать из `backend/`: пути к настройкам в `SETTINGS_FILES_FOR_DYNACONF`
относительные, из корня репозитория конфиг не найдётся.

```bash
cd backend
export ROUTER_AI_API_KEY=...
python3 evals/qa/run_eval.py --label baseline          # весь набор
python3 evals/qa/run_eval.py --only multi_doc          # одна группа
python3 evals/qa/run_eval.py --only qa-008 --workers 1 # один кейс
```

Без ключа доступны два режима:

```bash
python3 evals/qa/run_eval.py --dry-run        # валидация набора: имена проверок, наличие документов
python3 evals/qa/run_eval.py --prepare-only   # сколько документов доезжает до графа
```

`--prepare-only` меряет подготовку состояния, где LLM не участвует. Это
единственная часть замера, которая работает без ключа, и именно она ловит потерю
документов.

Полезные флаги: `--chunk-threshold 1500` — понизить порог чанкования, чтобы
прогнать RAG-ветку на коротких документах, не заводя стокилобайтный договор.

Отчёты — `reports/<label>.md` и `.json`.

## Набор

| Группа | Кейсов | Что меряет |
|---|---|---|
| `summary` | 7 | Краткое содержание: реквизиты на месте, даты не противоречат друг другу и не выдуманы |
| `qa_fields` | 10 | Вопрос про конкретное поле: сумма, срок, код, реквизит |
| `multi_doc` | 6 | Два документа в сообщении и документ из прошлого хода |
| `anonymization` | 6 | Вопрос с настоящей фамилией по обезличенному тексту |
| `honesty` | 6 | Где данных не хватает — сказать об этом, а не достроить |

Документы в `docs/`: две выписки ЕГРН (настоящие, из `land_area/sample_data`),
ДКП квартиры, доверенность и справка 2-НДФЛ (составлены под кейсы, обезличены как
в проде). **Их нужно заменить на документы заказчика**, когда они появятся: набор
писался по скриншотам, а это хуже оригинала.

## Проверки

Гигиена включена во всех кейсах без объявления — это требование к любому ответу:

| Проверка | Ловит |
|---|---|
| `no_jargon` | «лицевой токен», «идентификатор», «чанк» — внутренняя кухня в ответе юристу |
| `no_fragment_markup` | «фрагмент D1–F1», «=== ДОКУМЕНТ ===», «в предоставленных фрагментах» |
| `no_anonymization_talk` | рассуждения про обезличивание и маскирование |

Сами токены `[PER_1]` в ответе допустимы: они восстанавливаются ниже по конвейеру.
Недопустимо их обсуждать.

Остальные объявляются в кейсе:

| Проверка | Аргумент | Смысл |
|---|---|---|
| `no_absence_claim` | список сущностей | не объявлять отсутствующим того, кто скрыт за токеном |
| `no_contradiction` | список сущностей | в одном ответе нет и отрицания, и утверждения о сущности |
| `covers_documents` | — | каждый документ отражён (якоря в `document_anchors`) |
| `no_conflicting_dates` | — | один реквизит не имеет двух разных дат |
| `no_invented_dates` | — | все даты ответа есть в документах |
| `declares_missing_document` | — | сказано, что для ответа не хватает документа |
| `must_contain_all` / `must_contain_any` / `must_not_contain` | список | точные значения |
| `must_match` / `must_not_match` | регулярки | форма ответа |
| `max_chars` / `min_chars` | число | объём |

Служебные ожидания кейса: `expect_intent` (`summarize` / `document_qa`),
`expect_attached` (сколько документов доехало до графа), `expect_stub`.

Сами детекторы покрыты тестами на реальных текстах с ответов, на которые жаловался
заказчик: `tests/evals/test_qa_checks.py`. Если детектор перестанет их ловить,
отчёт позеленеет на тех же дефектах.

## Что уже показал

Прогон `--prepare-only` на текущем коде: **30/35**, и все пять промахов — группа
`multi_doc`. До графа доезжает один документ вместо двух: `DocumentService._prepare`
берёт `file_ids[-1]`. Проверка не зависит от LLM и падает детерминированно, пока
обрезка на месте.
